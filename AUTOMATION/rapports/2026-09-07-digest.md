## Ce qui a bougé

**Le playbook.** `AUTOMATION/playbooks/01-loop-projet.md` étape 0 porte maintenant la
règle en tête, avec cet incident cité en exemple : lire **TOUTES** les PR ouvertes du
dépôt cible (`list_pull_requests(state="open")`), pas seulement les siennes. Une PR verte
qui attend depuis des jours n'est pas un obstacle, c'est du travail déjà fait.

C'est la correction la plus utile de la journée. Elle coûte une requête ; son absence a
coûté une matinée. Sur AgroTrack BF, elle a immédiatement révélé la PR #15, en attente
depuis 27 jours.

**AgroTrack BF, le mobile.** La barre latérale faisait 240 px en dur, à toutes les tailles.
Sur un Android de 360 px, elle prenait les deux tiers de l'écran et laissait 120 px à
l'application. Aucun point de rupture dans les 16 pages, pour un produit dont la vision dit
que l'utilisateur cible n'a pas d'ordinateur. Ce n'était pas une finition manquante, c'était
le cas nominal qui ne marchait pas. Tiroir mobile, tableaux qui défilent dans leur cadre,
13 tests. 133 verts, lint propre, build 0 erreur.

**AgroTrack BF, le vrai écart.** Le projet **n'enregistre aucune donnée**. Supabase ne sert
qu'à l'authentification ; les 16 pages affichent des constantes `MOCK` écrites en dur. On
rafraîchit, tout revient à l'état initial. Et « offline-first », promis dans la description
du dépôt et dans les métadonnées de l'application, **n'existe nulle part dans le code** :
pas de service worker, pas d'IndexedDB, pas de file de synchro, pas même de `localStorage`.

C'est une bonne maquette — 16 écrans cohérents, charte tenue, tests. Ce n'est pas un
logiciel qu'une coopérative peut utiliser. Entre AgroTrack BF et le KPI de la Phase 1, il
manque la couche de données entière. Question posée dans
`AUTOMATION/questions/agrotrack-bf.md`, hypothèse retenue : on la construit.

## Le soir : AgroTrack BF a un squelette

Second passage sur AgroTrack BF, [PR #18](https://github.com/dosteeve2-hash/agrotrack-bf/pull/18).
Six tables, RLS sur les six, et la page Membres branchée de bout en bout. Les douze
producteurs de la maquette deviennent un `seed.sql` : la même donnée, mais du côté où
on peut la modifier.

**J'ai changé la page témoin en cours de route.** J'avais annoncé Collectes ; le PRD
met les collectes en Phase 2 parce qu'elles n'ont d'intérêt qu'avec la synchro hors
ligne. Membres et parcelles tiennent debout tout de suite. La spec tranche, pas ma
note de la veille.

**Aucune base n'a été créée, aucune migration exécutée** — c'est une action de
production, elle t'appartient. Le prix assumé : le SQL est relu, pas éprouvé. La
première application peut révéler une erreur.

Et « offline-first » reste **une promesse, pas un fait** : `client_id` et
`saisie_hors_ligne` sont posés, mais il n'y a ni service worker, ni IndexedDB, ni
file d'attente. C'est le vrai chantier, et il vient après ta validation du modèle.
