et un vérificateur de liens de projets. Quelqu'un a bien travaillé ici.

## 2. Le trou que ces garde-fous ne voient pas

`check-messages.mjs` vérifie que les trois locales ont **la même forme** et qu'aucune valeur
n'est vide. Nécessaire — mais il ne dit rien d'une clé **renommée dans les trois fichiers à la
fois** : le contrôle reste vert pendant que la page affiche le chemin brut de la clé.

Le cas dangereux est celui des clés **dynamiques** :

```ts
const FACTS = [{ labelKey: "locationLabel", valueKey: "locationValue" }, …]
…
{t(fact.labelKey)}
```

Aucune recherche de `t("…")` ne voit ces clés. Et le motif n'est pas isolé — la navigation, les
compétences et les statistiques fonctionnent pareil : **28 des 103 clés ne sont atteignables que
par ce chemin.**

Sur un portfolio, la conséquence n'est pas un plantage : c'est `about.availValue` affiché en
toutes lettres à un recruteur, sur la page qui doit précisément inspirer confiance.

## 3. Ce que j'ai construit — PR #10

`scripts/check-i18n-usage.mjs`, dans l'idiome exact du dépôt : Node pur, aucune dépendance
ajoutée, code de sortie non nul, câblé en CI juste après la synchro des locales.

Il relève les espaces de noms de `useTranslations("…")`, résout les clés statiques
(`t`, `t.rich`, `t.raw`, `t.markup`) **et** les clés de table — tout littéral affecté à une
propriété dont le nom se termine par `Key`.

**Un garde-fou qui dit toujours oui ne vaut rien**, donc j'ai provoqué les deux pannes pour de
vrai avant de les annuler :

| Épreuve | `check:messages` | `check:i18n-usage` |
|---|---|---|
| renommer `about.availValue` dans les 3 locales | ✓ **code 0** | ✗ *clé de table introuvable* — **code 1** |
| supprimer `about.bio1` des 3 locales | ✓ **code 0** | ✗ *clé introuvable* — **code 1** |

Dans les deux cas l'ancien contrôle est vert et la page est cassée.

**Vérifié : lint propre, 103 clés synchronisées, 100 clés appelées résolues, build 9 pages.**

## 4. Un choix que je signale

**Je n'ai pas ajouté de framework de test.** Le dépôt n'en a aucun et s'appuie sur des scripts
Node vérifiés en CI. Y greffer Vitest pour ce seul besoin aurait été une décision d'architecture
déguisée en correctif — et le script fait le travail avec zéro dépendance.

J'ai aussi supprimé le fichier **`master`** à la racine : une ligne,
`MERGE feat/projects-contact-0629 -`, visiblement une redirection de shell partie de travers. Un
fichier nommé `master` rend `git checkout master` ambigu. `deploy.ps1` et `do_merge.bat` sont
**laissés tels quels** — ils servent peut-être.

## 5. Ce que je n'ai pas fait

- Le dépôt n'a **aucun test** au sens strict. Ce n'est pas un manque criant sur un site vitrine
  statique de 9 pages, et les trois scripts couvrent ce qui casse en pratique.
- `check:links` renvoie **13 sondes non concluantes** (HTTP 403) : le proxy réseau de ma session
  filtre ces domaines. Ce n'est pas un défaut du dépôt, et je ne peux pas trancher d'ici si ces
  13 démos répondent réellement.
