# binary-search-tree-java — contrôle de santé du 15 septembre 2026

**Verdict : 🔴 la branche de nettoyage ne compile pas. Ne pas la fusionner en l'état.**

Hier, sur `Mon-Portfolio-`, une branche `chore/cleanup` du même jour était juste et je l'ai
recommandée à la fusion. Ici la branche porte le **même nom**, vient de la **même
campagne**, et elle est **fausse**. C'est la leçon du jour.

## Le défaut de fond : le code est livré en ZIP

Sur `main`, tout le projet tient dans **`BinarySearchTree.zip`**. Un dépôt git dont le
contenu est une archive compressée n'est pas un dépôt de code : pas de diff, pas de
`git blame`, pas de recherche, pas de revue. Le ZIP contient en plus :

- les **`.class` compilés** (artefacts de build versionnés),
- un dossier `.vscode/`,
- et une **copie imbriquée intégrale** : `BinarySearchTree/BinarySearchTree/` reprend les
  mêmes fichiers.

L'intention de `chore/cleanup` est donc la bonne : extraire les sources, supprimer le ZIP.

```
$ git diff --name-status origin/main origin/chore/cleanup
D  BinarySearchTree.zip
A  docs/AGAC_VERI_MODELI_PROJESI_RAPORU.docx
A  src/AVLTree.java
A  src/BinarySearchTree.java
A  src/TreeGUI.java
```

Avance rapide propre (`merge-base` = la pointe de `main`), `.class` et `.vscode` écartés,
nom de fichier turc translittéré en ASCII. Tout cela est bien fait.

## 🔴 Mais elle a extrait la mauvaise copie de `TreeGUI.java`

La copie imbriquée n'était pas un doublon strict. Empreintes des sources du ZIP :

| Fichier dans le ZIP | empreinte |
|---|---|
| `BinarySearchTree/AVLTree.java` | `6517c023` |
| `BinarySearchTree/BinarySearchTree/AVLTree.java` | `6517c023` — identique |
| `BinarySearchTree/BinarySearchTree.java` | `14361bbb` |
| `BinarySearchTree/BinarySearchTree/BinarySearchTree.java` | `14361bbb` — identique |
| `BinarySearchTree/TreeGUI.java` | **`e5ab243d`** ← retenue par la branche |
| `BinarySearchTree/BinarySearchTree/TreeGUI.java` | **`bf556fc5`** — différente |

Deux `TreeGUI.java` divergents. La branche a pris le plus récent (22 déc. contre 19 déc.).
Or c'est celui qui est cassé :

```java
    public static void main(String[] args) {

    javax.swing.SwingUtilities.invokeLater(() -> {
        new TreeGUI();
    });
}

    }
}
```

Une accolade en trop, et `new TreeGUI()` **sans `.setVisible(true)`** — alors que le
constructeur ne l'appelle pas non plus. La version du 19 décembre faisait
`new TreeGUI().setVisible(true);`.

## La preuve : compilé, les deux

```
$ javac -d out src/*.java            # version retenue par chore/cleanup
src/TreeGUI.java:179: error: class, interface, enum, or record expected
}
^
1 error                                                        → code 1

$ javac -d out <copie imbriquée du ZIP>                        → code 0
```

**La branche transformerait un dépôt dont le projet fonctionne (dans le ZIP) en un dépôt
dont le code visible ne compile pas.** C'est l'inverse de ce qu'elle cherche à faire.

## Ce que je n'ai pas fait

Playbook 02 : contrôle de santé, jamais de développement. Je n'ai **rien poussé, rien
fusionné, rien corrigé**. `main` reste intact — et `main` n'est pas cassé : le ZIP qu'il
contient renferme une version qui compile.

## Recommandation

Ne pas fusionner `chore/cleanup` telle quelle. La correction tient en un geste, au choix :

1. **Remplacer `src/TreeGUI.java`** par la copie imbriquée du ZIP (`bf556fc5`), qui
   compile ; ou
2. garder la version du 22 décembre et **retirer l'accolade en trop**, puis rétablir
   `setVisible(true)` — sans quoi la fenêtre ne s'affichera jamais.

Dans les deux cas, compiler avant de fusionner. Le reste de la branche est bon et mérite
d'être gardé.

## Règle acquise

> Une branche portant le **même nom** et venant de la **même campagne de nettoyage** peut
> être juste sur un dépôt et fausse sur son voisin. `Mon-Portfolio-` le 14, celui-ci le
> 15. La seule façon de savoir est de **l'exécuter** — ici, de la compiler.
