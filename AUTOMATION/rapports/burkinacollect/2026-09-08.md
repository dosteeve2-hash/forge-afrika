## 1. La branche par défaut de ce dépôt public contient deux fichiers

```
$ git ls-tree -r --name-only origin/main
README.md
hooks/useOfflineSync.ts
```

C'est tout. Pas de `package.json`, pas de `src/`, pas d'application. C'est ce qu'un `git clone`
récupère, ce qu'un visiteur de GitHub voit, et ce qu'une session Claude ouvre par défaut.

L'application — 17 fichiers, Next.js 16 — vit dans la PR **#4**, ouverte le 2 septembre et
laissée **en brouillon**.

## 2. Le README promet six fonctionnalités qui n'existent nulle part

Le README de `main` présente un produit fini : badges Next.js 16 / React 19 / TypeScript /
Tailwind, un lien **« 🌍 Voir le site live »** vers `https://burkinacollect.vercel.app`, et un
tableau de six fonctionnalités :

> Dashboard opérationnel · Form builder · Sync Queue offline · Gestion des agents ·
> Carte des zones · Dashboard superviseur

**Aucune de ces six fonctionnalités n'existe dans aucune branche du dépôt.** La branche la plus
avancée (PR #4) contient exactement deux routes : `/` (une page d'accueil) et `/about`.

Détail qui résume la situation : le README affiche son propre logo avec
`<img src="public/favicon.ico">` — un fichier qui **n'existe pas sur `main`**. Le logo est cassé
sur la page GitHub du projet.

Je n'ai pas pu vérifier si `burkinacollect.vercel.app` répond : le proxy réseau de ma session
bloque ce domaine. Ce que je peux dire, c'est que si Vercel construit ce site depuis la branche
par défaut, il ne peut pas y avoir d'application — `main` n'a pas de `package.json`.

C'est le point le plus important de ce rapport, et il n'est pas technique. **Le dépôt est
public.** Un investisseur, un recruteur ou un partenaire qui suit ce lien lit la description
d'un produit qui n'a pas été écrit. Ce n'est pas un bug, c'est un écart entre ce qui est annoncé
et ce qui est livré — et `PROJECT.md` fait justement de cette distinction le KPI de la Phase 1 :
*« déployé sur Vercel » n'est pas « utilisé par une entreprise réelle »*. Ici, on est un cran
avant : *« annoncé dans un README » n'est pas « déployé »*.

## 3. ⚠️ Le seul code de `main` perd des données terrain, en silence

`hooks/useOfflineSync.ts` est le seul fichier de code du tronc. Il contient un défaut qui, pour
ce produit précisément, est le pire possible.

Sur `main`, dans la boucle de vidage de la file :

```ts
for (const item of queue) {
  try {
    const ok = await syncFn(item);
    if (!ok && item.retries < MAX_RETRIES) {
      remaining.push({ ...item, retries: item.retries + 1 });
      hasError = true;
    }
  } catch { /* idem */ }
}
setQueue(remaining);
saveQueue(remaining);
```

Un item qui a épuisé ses `MAX_RETRIES` n'entre dans **aucune** branche du `if`. Il n'est donc pas
repoussé dans `remaining` — et `remaining` est ensuite écrit dans `localStorage` **à la place de
la file**. La soumission est effacée du stockage sans avoir été envoyée, sans erreur, sans trace.

Traduit en usage réel : **un agent de terrain remplit un formulaire dans une zone sans réseau ;
trois tentatives de synchronisation échouent ; sa saisie disparaît, et rien ne le lui dit.**

`VISION.md §4` dit exactement ce qu'il faut en penser : *« Robuste > élégant. Batterie faible,
stockage plein, coupure en plein formulaire : ce sont les cas nominaux, pas les cas limites. »*
Un outil de collecte offline-first qui perd silencieusement une saisie ne rate pas un cas
limite — il rate sa raison d'être.

## 4. La PR #4 corrige tout cela, et elle est en brouillon depuis le 2 septembre

Elle extrait la boucle dans une fonction pure `processQueue()`, testable sans React, et sépare
trois issues au lieu de deux : `synced`, `remaining` (à retenter), et **`failed`** — les items
épuisés, qui remontent désormais au hook via `failed` / `failedCount` au lieu d'être effacés.
Le commentaire du code dit la chose franchement : *« Ils ne sont PAS perdus. »*

Vérifiée en local, sur la branche telle quelle :

| Contrôle | Résultat |
|---|---|
| `npx eslint .` | **0 erreur** |
| `npx vitest run` | **6 / 6** (aucun test n'existait avant) |
| `npm run build` | **passe** — 3 routes, 106 kB de JS au premier chargement |

Elle apporte aussi la CI (`.github/workflows/ci.yml`), que le dépôt n'a pas.

**Elle est en brouillon.** C'est très probablement la seule raison pour laquelle elle n'a pas été
regardée : un brouillon ne demande rien à personne. CodeRabbit ne relit pas les brouillons non
plus.

## 5. La PR #3 est absorbée par la #4

`feat/about-landing-0629` (29 juin, 14 fichiers) contient la même page d'accueil et la même page
`/about`. La #4 les reprend, en corrigeant `next.config.ts`, en remplaçant `.eslintrc.json` par
`eslint.config.mjs`, et en ajoutant les tests et la CI.

**Fusionner la #4 rend la #3 sans objet.** Elle se ferme alors sans rien perdre.

## 6. Ce que je recommande, par ordre

1. **Sortir la PR #4 du brouillon et la fusionner.** L'application arrive enfin sur `main`, la
   perte de soumissions est corrigée, et le dépôt gagne une CI.
2. **Fermer la #3** — absorbée.
3. **Corriger le README** pour qu'il décrive ce qui existe (une page d'accueil, une page
   `/about`, un hook de synchronisation offline testé) plutôt que six fonctionnalités à écrire.
   Les six peuvent rester, dans une section « feuille de route ». **Je ne l'ai pas fait :
   réécrire la promesse publique d'un projet est ta parole, pas la mienne** — c'est la même
   limite que pour `PROJECT.md` et `VISION.md` (protocole §3, règle 10).
4. **Vérifier ce que sert `burkinacollect.vercel.app`**, que je ne peux pas atteindre.

## 7. Pourquoi je n'ai rien construit malgré 2 PR seulement

Le seuil de triage n'est pas la seule raison de ne pas construire. Ici, écrire du code aurait
voulu dire l'une de ces deux choses : le poser sur un `main` sans application — donc réinventer
la PR #4 — ou brancher depuis la PR #4 et empiler une PR sur une PR en brouillon que personne
n'a encore regardée. Les deux aggravent le problème au lieu de le traiter.

**Le blocage de BurkinaCollect n'est pas un manque de code. C'est que le code écrit n'a jamais
été publié.**
