## 1. Une hypothèse que j'ai eu tort de faire, et que j'ai vérifiée

Premier réflexe, après MillTrack : compter les points de rupture responsive.

```
$ grep -c "md:\|sm:\|lg:" sur chaque .tsx de app/ et components/
→ 0 partout
```

J'ai failli conclure que SUGU n'était pas utilisable sur téléphone. **C'était faux.** SUGU ne
fait pas son responsive en classes Tailwind mais en **media queries CSS**, dans
`app/globals.css` : sous 768 px la barre latérale devient un tiroir (`.sugu-sidebar` en
`translateX(-100%)`, `.open` pour l'ouvrir), une barre de navigation basse apparaît
(`.sugu-bottom-nav`), les grilles de KPI se replient, et sous 480 px la grille de caisse passe à
2 colonnes.

C'est même **le dépôt le mieux pensé pour le mobile de tout le portefeuille** : un `BottomNav`
avec bouton central Caisse, masqué sur la page `/caisse` elle-même. Il n'y avait rien à corriger
de ce côté.

La leçon vaut d'être notée : **compter les `md:` mesure une technique, pas une intention.**

## 3. ⚠️ Le vrai défaut : une vente non enregistrée s'affiche comme enregistrée

Toutes les données de SUGU vivent dans `localStorage` — ventes, produits, stock, clients,
crédits. Il n'y a pas de serveur : c'est ce qui rend l'application utilisable sans réseau, et
c'est aussi son seul stockage. `lib/storage.ts` écrivait ainsi :

```ts
try {
  window.localStorage.setItem(key, JSON.stringify(next))
} catch {
  // storage full or unavailable — data stays in memory for this session
}
return next
```

Le commentaire dit vrai, et c'est le problème. Quand `localStorage` refuse l'écriture, l'échec
est avalé et `next` est **quand même renvoyé** : l'écran continue d'afficher la vente que le
commerçant vient d'encaisser, alors qu'elle n'a pas été enregistrée. Il ferme l'onglet, elle a
disparu, et rien ne le lui a dit.

`VISION.md §4` nomme le cas explicitement : *« batterie faible, **stockage plein**, coupure en
plein formulaire : ce sont les cas nominaux, pas les cas limites. »* Sur un Android d'entrée de
gamme utilisé toute la journée, le stockage plein n'est pas une hypothèse d'école — et il n'y a
aucun serveur derrière pour rattraper.

**C'est le deuxième dépôt du jour avec ce défaut exact.** BurkinaCollect perdait les soumissions
terrain épuisées après `MAX_RETRIES` ; SUGU perd les ventes quand le disque est plein. Deux
produits différents, deux équipes-sessions différentes, la même faute : **une écriture qui
échoue et une interface qui dit que tout va bien.**

## 4. Ce que j'ai construit — PR #12

- **`lib/persistance.ts`** — `ecrireLocal()` retourne l'échec au lieu de l'avaler, et distingue
  le **quota** (mémoire pleine) de l'**indisponibilité** (navigation privée, stockage bloqué) :
  les deux n'appellent pas le même geste de la part du commerçant. Le quota est reconnu par le
  nom de l'erreur **et** par les codes 22 et 1014 — les navigateurs ne renseignent pas tous les
  mêmes champs.
- Un **registre d'échecs** plutôt qu'un contexte React : `usePersisted` est appelé par quatorze
  pages, aucune n'a à connaître ce mécanisme.
- **`components/AlerteStockage.tsx`** — un bandeau `role="alert"` qui dit **de ne pas fermer la
  page** et quoi faire selon la cause. Monté une fois dans `AppShell`, écran d'accueil compris
  (il écrit aussi). `no-print` : il n'a rien à faire sur un ticket de caisse.
- **`lib/storage.ts`** — l'écriture sort de l'updater de `setValue` : React peut rejouer un
  updater, un effet de bord n'a rien à y faire. Une `ref` porte la valeur courante, ce qui garde
  les mises à jour fonctionnelles correctes même en rafale.

**Vérifié : 80 tests (64 avant, +16), lint 0 erreur et 32 avertissements — exactement la base,
mes fichiers n'en ajoutent aucun —, `tsc` propre, build 18 routes.**

## 5. Une décision d'ingénierie à signaler : la PR est empilée

C'est délibéré. Sur `master`, `npm test` est rouge : toute PR que j'y ouvrirais hériterait d'une
suite qui ne passe pas, et mon protocole §6 interdit de pousser sans tests verts. Les trois
options étaient :

1. dupliquer la configuration de test de la #11 → deux PR qui écrivent les mêmes fichiers ;
2. livrer le correctif sans test → un correctif de perte de données non testé, non ;
3. empiler sur la #11.

J'ai pris la 3. GitHub re-ciblera la #12 sur `master` automatiquement quand la #11 sera
fusionnée. Ce n'est **pas** la situation que j'ai critiquée chez BurkinaCollect : là-bas, la PR
support était un **brouillon que personne n'avait lu**. Ici la #11 est une PR ouverte,
normale, que j'ai moi-même vérifiée verte.
