## Le mécanisme, ligne par ligne

`lib/storage.ts` au tronc, fonction `update` :

```ts
setValue((prev) => {
  const next = typeof updater === 'function' ? updater(prev) : updater
  try {
    window.localStorage.setItem(key, JSON.stringify(next))
  } catch {
    // storage full or unavailable — data stays in memory for this session
  }
  return next
})
```

Et `app/caisse/page.tsx`, la validation d'une vente :

```ts
setVentes((prev) => [vente, ...prev])
```

Deux défauts, dont un seul se voit :

1. **L'écriture est un effet de bord placé dans un updater de `setValue`.** React peut
   rejouer un updater ; ce n'est pas un endroit pour une entrée-sortie.
2. **Le `catch` est muet.** Si l'écriture échoue — stockage plein, navigation privée, quota
   dépassé — la vente n'existe plus que dans la mémoire de React. Le commerçant voit son
   reçu, l'imprime, le partage… et la vente disparaît à la fermeture de l'onglet. Le
   commentaire lui-même l'admet (« data stays in memory for this session ») sans que
   personne, à l'écran, ne l'apprenne.

Et `VISION.md §4` est formel : « Batterie faible, **stockage plein**, coupure en plein
formulaire : ce sont les **cas nominaux**, pas les cas limites. » Sur un Android d'entrée de
gamme, ce n'est pas un cas rare, c'est mardi.
