## 1. Ce dépôt n'est pas comme les autres

FORJA et MillTrack avaient le même problème : un tronc qui a avancé pendant que les PR
dormaient, donc des PR périmées. **Ici, l'inverse : le tronc n'a pas bougé depuis le 27 juin.**

Conséquence directe : **aucune des 6 PR n'est périmée.** Cinq d'entre elles sont à zéro commit
de retard, la sixième à trois. Il n'y a rien à fermer. Il y a six PR encore valables et personne
pour les fusionner.

## 2. Le tronc a une CI qui n'a jamais pu passer

En lisant la PR #7 j'ai compris pourquoi ce dépôt est figé. Les deux workflows de `main` sont
structurellement rouges, pour trois raisons indépendantes :

| Cause | Effet |
|---|---|
| `node-version: '18'` alors que Next 16 exige Node ≥ 20 | le job ne démarre pas |
| `actions/upload-artifact@v3` — **désactivée par GitHub depuis janvier 2025** | l'étape échoue |
| `coverageThreshold` global à 50 % alors que la couverture réelle est de **19,98 %** | `npm test` sort en code 1 même avec 50 tests au vert |

Ce n'est pas « la CI est instable ». C'est **une CI qui ne pouvait pas réussir**, quoi qu'on
pousse. Un dépôt dans cet état ne fusionne rien, et c'est exactement ce qu'on observe : la PR la
plus ancienne date du 10 juin.

Troisième dépôt du portefeuille où le même correctif — *réparer la CI + le lint* — attend :

| Dépôt | La PR | État |
|---|---|---|
| MillTrack | #12, 2 sept. | ✅ **fusionnée** → tronc vert |
| FORJA | #27, 2 sept. | ⏳ ouverte → tronc rouge depuis un mois |
| African Hybrid Agent | **#7, 2 sept.** | ⏳ ouverte → tronc figé depuis 73 jours |

## 3. ⚠️ La PR #7 n'est pas de l'hygiène : elle borne une dépense

`/api/chat` est le seul endpoint qui appelle un modèle. Sur `main` aujourd'hui :

- **aucune limite de débit** — `git grep -il "ratelimit\|throttle" -- src` sur `main` ne renvoie
  **rien** ;
- **aucune authentification** sur cet endpoint (les deux routes `/api/admin/*` sont gardées,
  elles ; le reste — `chat`, `corpus`, `evidence`, `search/vector`, `analytics`, `audit`,
  `cache` — est ouvert) ;
- `src/lib/llm/generate.ts` route vers **Anthropic ou OpenAI** dès que `ANTHROPIC_API_KEY` ou
  `OPENAI_API_KEY` est défini (à défaut il tombe sur Ollama en local).

Autrement dit : **si ce dépôt est déployé quelque part avec une clé d'API renseignée, n'importe
qui peut boucler sur `/api/chat` et facturer la clé.** Je ne peux pas vérifier ce point — lire
les variables d'environnement d'un déploiement est une action de production, hors de mes limites
(`00-protocole-forge.md §3`). Le README ne mentionne pas d'URL de production pour ce dépôt-ci.
**C'est donc une question pour Steeve, pas une affirmation de ma part.**

Ce que je peux affirmer : la règle est écrite dans le `CLAUDE.md` de Steeve — *« Tout endpoint
touchant Anthropic/OpenAI doit avoir un rate limit. Max 20 requêtes/utilisateur/heure »* — et le
tronc ne la respecte pas, alors que le correctif est écrit, testé et en attente depuis le
2 septembre.

**Bonne nouvelle : rien n'est exposé côté secrets.** Vérifié : aucun fichier `.env` versionné
(seul `.env.example`), et aucune chaîne ressemblant à une clé réelle dans l'arbre de `main`.

## 4. La PR #7 est juste — mais elle est noyée

Le limiteur (`src/lib/rate-limit.ts`, 114 lignes) est du bon travail : compteur Redis avec repli
en mémoire, `shared: false` quand Redis manque — donc honnête sur ce qu'il garantit —, `429` avec
`Retry-After` et `RateLimit-*`, et un commentaire qui dit franchement que l'identification par IP
est usurpable mais borne l'abus le plus courant. 98 lignes de tests l'accompagnent.

**Le problème est ailleurs : la PR contient 39 124 lignes ajoutées pour ~240 lignes utiles.**
Elle versionne tout le dossier `coverage/` — 80 fichiers de rapport HTML/JSON générés par Jest.
Pire, son `.gitignore` ajoute `*.tsbuildinfo` **mais pas `coverage/`** : le dossier est donc
commité *et* non ignoré.

**Recommandation : ne pas fusionner telle quelle.** Retirer `coverage/` de l'historique de la
branche et l'ajouter au `.gitignore`, puis fusionner. Les 5 fichiers qui comptent sont
`src/lib/rate-limit.ts`, `src/lib/__tests__/rate-limit.test.ts`, `src/app/api/chat/route.ts`,
et les deux workflows.

**Une réserve technique à signaler à celui qui la reprendra** : dans le chemin Redis, le
compteur fait un `get` puis un `set` — ce n'est pas atomique. Deux requêtes simultanées peuvent
lire la même valeur et ne l'incrémenter qu'une fois. `INCR` + `EXPIRE` serait exact. Ça ne
retire rien à l'utilité de la PR (la borne reste posée), mais sous charge la limite est plus
lâche que 20.

`STATUS_FINAL.md`, `FINAL_STATUS.md`, `WORK_COMPLETED.md`, `CONTINUATION_SUMMARY.md`… — plus des
artefacts de test commités (`test_output.txt`, `test_results.json`, `tsconfig.tsbuildinfo`). La
#2 range tout ça. C'est la seule des six qui demande un travail avant fusion : ramener `main`
dedans (3 commits de retard) et arbitrer le conflit probable sur `.gitignore` avec la #7.

## 7. Ce que ce triage ajoute au diagnostic du portefeuille

Le recensement du 7 septembre disait : *« le code ne manque pas, les fusions manquent »*. FORJA a
nuancé : *sur 12 PR, 11 sont à fermer.* **African Hybrid Agent renverse encore la nuance : ici,
les 6 sont à fusionner.**

La différence tient à une seule variable — **le tronc a-t-il bougé ?** Quand il avance sans les
PR (FORJA, MillTrack), elles pourrissent. Quand il s'arrête (ici), elles restent bonnes et c'est
la CI cassée qui bloque tout. Dans les deux cas la cause est la même : **personne ne fusionne.**
Mais le remède n'est pas le même, et un loop qui ne regarde pas la date du tronc se trompera de
remède.
