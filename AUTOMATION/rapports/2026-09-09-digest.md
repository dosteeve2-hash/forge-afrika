# Digest — 2026-09-09

Deux projets : **TAAMA** et **CompTrack**, les deux plus grosses piles du portefeuille. Les deux
en mode triage. **Rien construit** — et dans les deux cas c'était la bonne décision, pour la même
raison : *les PR de ces dépôts ne sont pas en retard, elles visent des branches qui ne peuvent
pas les recevoir.*

---

## TAAMA — le tronc est un commit orphelin

```
$ git rev-list --count origin/main
1
```

`main` contient **un seul commit**, `3f8318d` du 10 août, **sans parent**. L'historique de
TAAMA — la v1.0 de juin, tout juillet — a été remplacé, pas continué.

Conséquence : `git merge-base origin/main origin/<branche>` ne renvoie **rien** pour **17 des 18
PR ouvertes**. Ce ne sont pas des PR en retard, ce sont des PR que git ne peut pas fusionner.
GitHub les affiche comme ouvertes ; elles ne le sont qu'en apparence.

**Ce que le remplacement a gardé, et ce qu'il a perdu.** J'ai d'abord cru que tout était perdu,
puis que tout était sauvé ; les deux étaient faux.

- **Gardé et enrichi — le tableau de bord.** `main` a toutes les pages de l'ancienne histoire
  plus sept nouvelles, et en plus complet : `inventaire/page.tsx` fait **591 lignes** contre
  **29** avant.
- **Perdu — tout le site public.** `/pricing`, `/demo`, `/contact`, `/tarifs`, `/blog`
  n'existent **nulle part ailleurs** que dans deux PR orphelines : la **#10** et la **#12**.

D'où le tri : **15 PR fermables sans rien perdre, 2 à sauver par extraction de fichiers** (aucune
fusion n'est possible), **1 à fusionner** — la #35, vérifiée : lint 9 erreurs → 0, une **suite de
tests entière** débloquée (110 → **169**), build 20 routes. C'est **Q14**.

**Mon erreur, à corriger.** J'ai « traité » TAAMA le 7 septembre : j'ai corrigé mon compte de PR
et fermé un doublon, mais je n'ai pas vu que le tronc était orphelin — donc que les PR que je
comptais étaient inertes. J'ai compté une pile sans vérifier qu'elle tenait debout.

## CompTrack — dix-sept PR visent la mauvaise branche

La branche par défaut est **`feat/comptrack-v1`**, pas `main`. Or **17 des 21 PR ouvertes visent
`main`**. Elles pointent vers une branche que le produit n'utilise pas.

| | `feat/comptrack-v1` (défaut) | `main` |
|---|---|---|
| Pages | **24** — dont `connexion`, `inscription`, `bilan`, `contrats`, `declarations`, `employes`, `paie`, `tresorerie` | 20 — dont `catalogue`, `vente-rapide` |
| Authentification | oui | **aucune** |

Mesurées contre le **vrai** tronc, trois PR sont intégralement absorbées : la **#23** (64
fichiers ajoutés, **64 déjà présents**), la **#22** (19/19) et la **#21** (20/21). Les quatorze
autres demandent une relecture — mais seulement **après** avoir tranché quelle branche est le
tronc, sinon on compare à la mauvaise référence. C'est **Q15**.

Sur le vrai tronc : le build passe (29 pages), mais **6 tests échouent sur 72** et surtout
**`npx eslint` ne démarre pas** — il n'y a aucun `eslint.config.mjs`. Ce n'est pas du lint sale,
c'est *pas de lint*. Sur un SaaS de comptabilité — TVA, SYSCOHADA, paie. La **PR #38** corrige
tout, sur la bonne branche : **72/72**, ESLint fonctionne, build 29 pages.

## Une erreur de méthode, attrapée à temps

Mes premières mesures sur CompTrack disaient *build cassé, aucun test, aucun lint*. C'était faux :
le clone local, hérité d'une session précédente, était en **sparse checkout à 16 %** —
`app/`, `components/`, `lib/`, `__tests__/` absents du disque. Et `git status` affichait
**« working tree clean »**.

Tout a été remesuré après `git sparse-checkout disable`. La règle qui en sort : **vérifier son
propre environnement avant d'accuser le dépôt.** Un outil qui ment poliment est plus dangereux
qu'un outil qui plante.
