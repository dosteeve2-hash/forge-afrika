## J'ai changé la page témoin, et voici pourquoi

Ce matin j'avais annoncé **Collectes**. Le `PRD.md` de Steeve dit autre chose :

> Phase 1 — Gestion membres et parcelles
> Phase 2 — Module collectes offline

Les collectes n'ont d'intérêt qu'avec la synchro hors ligne, qui n'existe pas.
Membres et parcelles tiennent debout tout de suite. J'ai suivi le PRD plutôt que
ma note de la veille — c'est la spec qui tranche, pas ma mémoire.

## Ce que j'ai construit

**Six tables** — `cooperatives`, `profils`, `membres`, `parcelles`, `collectes`,
`paiements` — avec RLS sur les six.

Trois décisions structurent le fichier :

1. **Le FCFA est un entier.** `integer`, jamais `numeric(_, 2)`. Le XOF n'a pas de
   sous-unité : arrondir un paiement à deux décimales n'est pas de la précision,
   c'est un bug qui attend son heure. Les hectares gardent leurs décimales — ce
   sont des surfaces, pas de l'argent.
2. **Une coopérative ne lit jamais les données d'une autre**, et c'est Postgres qui
   l'impose, pas le code des pages. La clé anonyme circule dans le navigateur ;
   sans RLS, elle lirait toute la base.
3. **`client_id` prépare la synchro hors ligne.** Le terminal génère l'identifiant
   avant l'envoi ; un renvoi après coupure retombe sur la même ligne au lieu
   d'enregistrer deux fois la même collecte. Une colonne aujourd'hui, une migration
   douloureuse sur données réelles plus tard.

**Le modèle corrige la maquette.** Elle donnait à chaque membre une culture et une
surface. Sur le terrain, un producteur cultive du coton sur une parcelle et du
sésame sur une autre : c'est le cas normal. Surface et culture vivent donc sur la
parcelle.

Détail qui vaut d'être noté : le composant `MembresClient.tsx`, que j'avais signalé
ce matin comme code mort, portait **déjà ce modèle** (`parcelles: number`,
`produits: string[]`). Ce n'était pas du déchet, c'était la bonne intention restée
en plan. J'ai eu tort de le ranger avec les orphelins sans le lire.

**Les 12 producteurs de `MEMBRES_INIT`** deviennent `supabase/seed.sql` — mêmes noms,
mêmes villages, mêmes surfaces, mais du côté où on peut les modifier. Une maquette
devenue fixture.

129 tests verts (120 + 9 sur l'agrégation), lint propre, build 0 erreur.

## La limite que je me suis imposée

**Aucun projet Supabase créé, aucune migration exécutée.** C'est une action de
production, elle appartient à Steeve (protocole §3.6). Ce sont des fichiers SQL
versionnés et relus, rien d'autre.

Conséquence assumée : tant que la migration n'est pas appliquée, `/membres` affiche
l'erreur Supabase. Mieux vaut un message franc qu'une liste vide qui ressemble à une
coopérative sans membres.

Conséquence moins confortable : **je n'ai aucune preuve d'exécution.** Le SQL est
relu, pas éprouvé. La première application peut révéler une erreur de syntaxe ou une
politique RLS mal fermée. C'est le prix de la règle, et il vaut d'être payé.

## Ce qui reste, et c'est le plus gros

« Offline-first » est toujours **une promesse, pas un fait**. `client_id` et
`saisie_hors_ligne` sont posés ; il n'y a ni service worker, ni IndexedDB, ni file
d'attente. C'est la Phase 2 du PRD et le vrai chantier.

Les 15 autres pages sont toujours en `MOCK`. Une page branchée prouve la chaîne ; la
répliquer vient après validation du modèle par Steeve.
