## 3. Ce que j'ai construit — PR #13

Le tableau de bord était **inutilisable sur la cible de `VISION.md §4`**, un Android de 360 px.
Trois défauts cumulés, tous vérifiés dans le code avant d'y toucher :

1. **La barre latérale ne disparaissait jamais.** `w-64 flex-shrink-0`, et
   `grep -c "md:\|sm:" app/(dashboard)/layout.tsx` → **0**. Sur 360 px : 256 px de barre,
   **104 px de contenu**.
2. **Trois tableaux emportaient la page.** Lots (10 colonnes), Stocks (8), Commandes (8) sans
   conteneur défilant : le défilement horizontal était celui du document, donc les titres et la
   navigation partaient avec. Ventes, Production et Maintenance avaient déjà `overflowX: auto` —
   c'était un oubli, pas un choix.
3. **Neuf grilles de KPI figées** à 3 ou 4 colonnes : ~80 px par carte sur téléphone.

Corrections :

- `components/DashboardNav.tsx` — barre latérale au-dessus de 768 px, tiroir en dessous (voile,
  fermeture au lien, au voile, à Échap). **Animé en CSS, pas avec framer-motion** : la dépendance
  est là, mais chaque kilo-octet de JS se paie sur un téléphone d'entrée de gamme en 2G/3G.
- `app/(dashboard)/layout.tsx` **redevient un Server Component** — il était `'use client'` en
  entier pour une liste de liens statique.
- `min-h-screen md:h-screen` : sur Android la barre d'adresse mange une partie de `100vh`.
- Les trois tableaux en `overflowX: auto` + `minWidth`.
- Les neuf grilles en `repeat(auto-fit, minmax(150px, 1fr))` — un mot par grille, aucune media
  query à maintenir, et le nombre de cartes étant fixe, `auto-fit` garde 3 ou 4 colonnes sur
  grand écran.

## 4. Ce que le lint m'a appris

Ma première version faisait l'évidence :

```ts
useEffect(() => setOuvert(false), [pathname])
```

`react-hooks/set-state-in-effect`, active dans ce dépôt, l'a refusée — appeler `setState`
directement dans un effet déclenche un rendu en cascade. La correction n'est pas un contournement,
c'est un meilleur modèle : mémoriser **le chemin sur lequel le tiroir a été ouvert** plutôt qu'un
booléen.

```ts
const [ouvertSur, setOuvertSur] = useState<string | null>(null)
const ouvert = ouvertSur === pathname
```

Toute navigation referme le tiroir sans qu'aucun effet n'ait à intervenir. Une règle de lint m'a
fait écrire moins de code, pas plus.

Deuxième surprise, dans les tests cette fois : `getAllByRole('link', { current: 'page' })` ne
renvoyait qu'**un** lien, pas deux. C'est correct — le tiroir fermé porte `aria-hidden="true"`,
donc ses liens sortent de l'arbre d'accessibilité. Mon test avait tort, pas le composant. Il est
devenu l'assertion inverse : un lecteur d'écran ne doit **pas** annoncer deux fois la même
destination.
